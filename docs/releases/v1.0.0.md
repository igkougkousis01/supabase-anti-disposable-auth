## Supabase Anti-Disposable Auth 1.0.0

Database-level disposable-email protection for Supabase projects, installed by one CLI.

Instead of validating throwaway addresses in application code — where a second client, a
mobile app or a dashboard invite routes straight around it — this pushes enforcement
into PostgreSQL and Supabase Auth. One policy engine, one list, one answer, consulted
before a user row is ever created.

## Install

```bash
npm install -g supabase-anti-disposable-auth
```

or run it without installing:

```bash
npx supabase-anti-disposable-auth --help
```

Requires **Node.js 22 or newer** and a Supabase project.

## Getting started

```bash
export SUPABASE_DB_URL='postgresql://...'

supabase-anti-disposable-auth doctor
supabase-anti-disposable-auth install
supabase-anti-disposable-auth sync
```

Then activate the hook on a hosted project — this is the step that actually filters
signups:

```bash
export SUPABASE_PROJECT_REF='...'
export SUPABASE_ACCESS_TOKEN='...'      # prefer .env or a secret manager

supabase-anti-disposable-auth hook enable --dry-run
supabase-anti-disposable-auth hook enable
supabase-anti-disposable-auth status
```

## What's in it

- **A policy engine in your database.** `guard.is_disposable_domain()` with canonical
  domain normalisation and allowlist precedence, installed by versioned,
  checksum-verified migrations.
- **The Before User Created hook**, which Supabase Auth calls inside the signup
  transaction and which fails closed.
- **Hosted activation** through the Supabase Management API, with conflict refusal and
  post-write verification.
- **Safe manual blocklist sync** — around 75,000 domains from a maintained upstream,
  under a full set of network and content safety checks.
- **Optional strict trigger mode** on `auth.users`, off by default, which also covers
  email changes.
- **Reversibility**: conservative `repair`, and an ownership-verified `uninstall` that
  never leaves Auth calling a deleted function.

## Key security properties

- The Management API token leaves the process only as an `Authorization: Bearer` header
  to a compiled-in HTTPS origin. Not in a URL, a log, an error, a file, a process
  argument — and not in `--debug` output either. Sentinel-token tests assert it.
- Connection strings are never printed; databases are named as `host:port/database`.
- All values sent to PostgreSQL are bound parameters; every identifier in DDL is
  compiled in.
- No `SECURITY DEFINER`, a pinned `search_path` on every function, and no privileges for
  `PUBLIC`, `anon` or `authenticated`.
- The hook and the strict trigger both **fail closed**.
- Nothing this tool does not own is ever overwritten — a foreign hook, a foreign trigger
  or an unprovable `guard` object is a conflict with its own exit code, never a target.
  There is no force flag.

## Limitations

- **Blocklist refresh is manual.** There is no scheduler in 1.0 —
  [here is why](../roadmap.md#why-there-is-no-scheduler-in-10). `sync` runs cleanly from
  cron, CI or a deploy step.
- **Installing is not enabling.** The hook function does nothing until Supabase Auth is
  configured to call it.
- **Strict mode is advanced and opt-in**, touches the Supabase-managed `auth.users`
  table, and fails closed.
- **Signups with no email are never blocked** — phone-only, anonymous and
  SSO-without-email flows are deliberately unaffected.
- **Uninstall spans two systems that cannot share a transaction.** Its ordering is
  verified and resumable; it is not atomic.

Full list: [README → Limitations](../../README.md#limitations).

## Upgrading

Nothing to upgrade. This is the first stable release, and no `0.x` build was ever
published to npm.

From here, the CLI surface — command names, flags and
[exit codes](../../README.md#exit-codes) — follows semantic versioning.
